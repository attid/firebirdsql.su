# UDF в Firebird: внешние функции и чем их заменяют

## Что такое UDF и где они встречаются

UDF (*User-Defined Function*, пользовательская функция) в Firebird — это внешняя функция, написанная на компилируемом языке программирования (обычно C, C++ или Free Pascal) и скомпилированная в динамическую библиотеку (`.dll` в Windows или `.so` в Linux). Сервер баз данных загружает такую библиотеку и вызывает функции напрямую из адресного пространства процесса. Чаще всего с UDF сталкиваются разработчики и администраторы при сопровождении или миграции унаследованных баз данных (в частности, Firebird 2.5 и более ранних версий), а также при исследовании чужих проектов, где исторически требовалась логика, отсутствовавшая в стандартном SQL.

## Объявление и удаление UDF

Чтобы внешняя функция стала доступна внутри базы данных, её необходимо зарегистрировать с помощью оператора `DECLARE EXTERNAL FUNCTION`. В объявлении указываются типы входных аргументов, способ передачи параметров, имя точки входа (*entry point*) и имя модуля (библиотеки).

Пример объявления функции из стандартной библиотеки `fbudf`:

```sql
DECLARE EXTERNAL FUNCTION add2
    INTEGER, 
    INTEGER
RETURNS INTEGER BY VALUE
ENTRY_POINT 'add2' MODULE_NAME 'fbudf';
```

Для удаления регистрации функции из метаданных базы данных используется оператор `DROP EXTERNAL FUNCTION`:

```sql
DROP EXTERNAL FUNCTION add2;
```

Среди готовых наборов UDF широкую известность получили библиотека `fbudf`, поставляемая вместе с дистрибутивом Firebird, а также популярная сторонняя библиотека `rfunc`.

## Почему от UDF отказываются

Исторически механизм UDF был необходим, так как ранние версии Firebird содержали ограниченный набор встроенных функций для манипуляции строками, датами и математическими вычислениями. Однако использование внешних библиотек связано с рядом архитектурных и эксплуатационных проблем:

1. **Риск падения сервера.** Поскольку UDF выполняется в адресном пространстве сервера, любая критическая ошибка в коде библиотеки (например, обращение по нулевому указателю или переполнение буфера) способна аварийно завершить работу всего процесса СУБД.
2. **Нестабильность сторонних решений и проблемы совместимости.** Библиотеки сторонней разработки часто перестают поддерживаться, требуют повторной сборки под новые платформы, разрядности (32/64 бит) или операционные системы.
3. **Безопасность.** Выполнение внешнего машинного кода требует строгого контроля за каталогами загрузки модулей (`UdfAccess` в конфигурации) и повышает риски компрометации сервера.
4. **Перенос возможностей в ядро.** Начиная с версии 2.1, в ядро Firebird перенесли множество базовых операций (например, строковые функции `LEFT`, `RIGHT`, `REPLACE`), а в Firebird 3.0+ набор встроенных средств существенно расширился, устранив необходимость во внешних модулях для типовых задач.

В современной официальной документации Firebird механизм UDF имеет статус устаревшего (*deprecated*).

## Чем заменять UDF

Для современных систем и при обновлении легаси-проектов применяются два основных подхода:

* **Встроенные функции ядра.** Для подавляющего большинства стандартных операций со строками, датами, числами и типами данных следует использовать стандартные функции Firebird. Они безопасны, оптимизированы и не требуют внешних зависимостей.
* **PSQL-функции (`CREATE FUNCTION`).** Начиная с Firebird 3.0, появилась возможность создавать полноценные пользовательские функции непосредственно на процедурном языке СУБД (PSQL) без компиляции DLL/SO. Такие функции хранятся внутри базы данных, переносятся вместе с резервной копией и изолированы от среды выполнения сервера.

## Рекомендации

При поддержке старых баз данных Firebird 2.5 рекомендуется провести аудит используемых UDF:
- Замените функции форматирования строк, математики и дат на стандартные встроенные аналоги ядра.
- Если планируется переход на Firebird 3.0 и новее, перепишите специфическую бизнес-логику на встроенные PSQL-функции через `CREATE FUNCTION`.
- Откажитесь от подключения непроверенных сторонних библиотек вроде `rfunc` в пользу штатных возможностей СУБД.
