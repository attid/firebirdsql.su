# nbackup: быстрое резервное копирование Firebird

Когда база Firebird вырастает до десятков или сотен гигабайт, логический бэкап через `gbak` превращается в проблему: часы ожидания, высокая нагрузка на диск и процессор. Для круглосуточных систем 24/7 штатным решением является **nbackup** — инструмент физического (постраничного) резервного копирования, входящий в дистрибутив Firebird начиная с версии 2.1.

В отличие от `gbak`, который читает каждую запись таблицы через транзакции, `nbackup` делает быстрый физический снапшот на уровне дисковых страниц прямо во время работы пользователей. Во время снятия копии все входящие транзакции перенаправляются во временный файл дельты (`.delta`), что гарантирует неизменность основного файла базы в момент копирования.

---

## nbackup против gbak: таблица сравнения

| Критерий | nbackup | gbak |
| :--- | :--- | :--- |
| **Принцип работы** | Физический (постраничный снапшот) | Логический (выгрузка данных и метаданных) |
| **Скорость создания** | Мгновенный снапшот / скорость I/O диска | Медленно (зависит от объема таблиц и индексов) |
| **Влияние на 24/7** | Минимальное, база продолжает работать | Высокая нагрузка на I/O, сборка мусора |
| **Инкрементальность** | Поддерживает уровни 0–8 через `.delta` | Нет (всегда полная копия) |
| **Сжатие данных** | Нет (размер равен исходному файлу) | Да (сжатый архив) |
| **Проверка целостности** | Нет (копирует повреждения «как есть») | Да (валидирует структуру записей) |
| **Миграция ODS/версий** | Не переносит между мажорными версиями | Да (позволяет сменить ODS и версию СУБД) |

---

## Основные команды

Инкрементальность строится на уровнях: уровень `-L 0` — полная физическая копия базы, уровни `-L 1..8` — инкременты изменений относительно предыдущего меньшего уровня.

- **Полный бэкап уровня 0 (быстрый снапшот):**
  ```bash
  nbackup -B 0 база
  ```
- **Инкрементный уровень 1:**
  ```bash
  nbackup -B 1 база backup1.nbk
  ```
- **Восстановление (слить дельты):**
  ```bash
  nbackup -R база backup0.nbk backup1.nbk
  ```
- **Фиксация дельты (после успешного копирования файла базы вручную):**
  ```bash
  nbackup -F база
  ```

---

## Восстановление базы

Процесс восстановления через `nbackup -R` последовательно накатывает цепочку инкрементов на базовую копию уровня 0, объединяя измененные страницы. 

Главное отличие: слитый файл — это не архив `.fbk`, а готовая копия страниц базы. После успешного завершения слияния файл не нужно распаковывать — достаточно просто переименовать его в `.fdb` и запустить сервер Firebird.

---

## Стратегия комбинирования

Не стоит полностью отказываться от `gbak` в пользу `nbackup`:
- **Маленькая база (до нескольких ГБ):** достаточно классического `gbak`.
- **Большая база (десятки и сотни ГБ) в режиме 24/7:**
  - `nbackup` — каждый час (быстрые инкременты, минимальный RPO без просадки производительности).
  - `gbak` — раз в сутки или раз в неделю (полноценная проверка целостности данных и сборка мусора).

## Грабли и подводные камни

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Разрастание дельты** | Пока база зафиксирована, файл `.delta` быстро растет от активной записи | Копировать файл снапшота сразу и немедленно вызывать команду фиксации (`-F`) |
| **Сломанная цепочка** | Попытка восстановить дельту без промежуточного уровня | Восстанавливать уровни строго по порядку: 0, затем 1, затем 2 |
| **Бэкап поврежденных страниц** | `nbackup` не валидирует логическую целостность | Помнить, что утилита не спасает от испорченной базы; совмещать с регулярным контролем |
| **Блокировки на старых версиях** | В ветке 2.5 присутствовали ошибки с deadlock при фиксации дельт | Обновляться на свежие релизы Firebird (3.0, 4.0, 5.0) |

## Что почитать дальше

- **gbak**: параметры логического резервного копирования, ключи сборки мусора и перенос между версиями ODS.
- **gstat**: анализ распределения страниц, оценка фрагментации и ранняя диагностика повреждений страниц базы данных.
