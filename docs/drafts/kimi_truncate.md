• # Как очистить таблицу в Firebird

  ## Короткий ответ

  В Firebird **нет команды TRUNCATE TABLE** — ни в 2.5, ни в 3.0, ни в 4.0. Это первое, что нужно принять, если вы пришли из PostgreSQL, MySQL или MSSQL. Вместо неё используются три подхода в зависимости от размера таблицы и вашей цели:

  - `DELETE FROM` — для маленьких и средних таблиц;
  - пакетное удаление частями через `EXECUTE BLOCK` — для больших;
  - пересоздание таблицы (`DROP` + `CREATE`) — радикальный вариант для огромных.

  Ниже — каждый способ с нюансами.

  ## Простой случай: DELETE FROM

  ```sql
  DELETE FROM orders_log;
  COMMIT;
  ```

  Удаляет все строки, и для таблицы на тысячи-другую записей этого достаточно. Но помните про побочные эффекты:

  - каждая удалённая строка пишется в журнал — на миллионах записей это медленно и раздувает файл базы;
  - генераторы (sequences) **не сбрасываются** — автоинкремент продолжит с того места, где остановился;
  - операция требует, чтобы не было активных транзакций, конфликтующих с таблицей;
  - после полного `DELETE` данные физически остаются в базе как «мусор» — стоит дождаться sweep или запустить сборку мусора вручную (`gfix -sweep`).

  ## Сброс генератора после очистки

  Очистили таблицу — почти всегда хотите обнулить счётчик ID:

  ```sql
  -- Firebird 3.0+
  ALTER SEQUENCE gen_orders_id RESTART WITH 0;
  ```

  Для Firebird 2.5 синтаксиса `ALTER SEQUENCE` нет, используется устаревший, но рабочий `SET GENERATOR` (удобно обернуть в `EXECUTE BLOCK`):

  ```sql
  EXECUTE BLOCK AS
  BEGIN
    EXECUTE STATEMENT 'SET GENERATOR gen_orders_id TO 0';
  END
  ```

  Важно: генераторы существуют вне транзакционного контекста — откат транзакции их не вернёт, и сбрасывать их надо явно.

  ## Большая таблица: удаляем частями

  Монолитный `DELETE FROM` на десятках миллионов строк — путь к раздутой транзакции и распухшему файлу базы. Правильнее удалять пакетами с коммитами между итерациями:

  ```sql
  EXECUTE BLOCK AS
  BEGIN
    DELETE FROM orders_log
    WHERE RDB$DB_KEY IN (
      SELECT RDB$DB_KEY FROM orders_log ROWS 10000
    );
  END
  ```

  Блок выполняется в цикле (из скрипта или хранимой процедуры), пока `ROW_COUNT` не станет равен нулю, с `COMMIT` после каждой порции. Альтернатива — `DELETE ... ROWS n`, либо удаление диапазонами по первичному ключу (`WHERE id BETWEEN :a AND :b`), тоже с коммитами между частями. Смысл один: не держать в одной транзакции миллионы изменений.

  ## Радикальный вариант: пересоздание таблицы

  Если таблица огромная и данные в ней не нужны вообще, быстрее всего — уничтожить и создать заново:

  1. Выгрузить метаданные: `isql -x` (извлечение DDL всей базы) и сохранить определение таблицы.
  2. `DROP TABLE orders_log;`
  3. Выполнить сохранённый `CREATE TABLE` заново.

  Это практически мгновенно и не создаёт мусора. Но учтите цену: вместе с таблицей теряются данные (разумеется), права (`GRANT`) нужно выдать заново, а зависимые объекты — триггеры, представления, процедуры, внешние ключи — пересоздать.

  Компромисс между «медленным DELETE» и «DROP» — обычный `DELETE FROM` с последующим sweep/garbage collection: структура, права и зависимости остаются на месте, а место со временем освобождается.

  ## Типичные грабли

  | Проблема | Причина | Что делать |
  |---|---|---|
  | DELETE «висит» часами, база растёт | Один гигантский DELETE без промежуточных коммитов — раздувает транзакцию и журнал | Удалять пакетами по 5–50 тыс. строк с COMMIT |
  | Ошибка при удалении: нарушение FK | Дочерние таблицы ссылаются на записи, а `ON DELETE CASCADE` не задан | Сначала очистить дочерние таблицы или пересоздать FK с каскадом |
  | ID новых записей не с 1 | Генераторы не сбрасываются автоматически | `ALTER SEQUENCE ... RESTART WITH 0` |
  | После DELETE файл базы не уменьшился | Удалённые версии строк — мусор, место переиспользуется, но не возвращается ОС | Sweep (`gfix -sweep`); физически ужать файл может только backup/restore |
  | `TRUNCATE TABLE` — syntax error | Такой команды в Firebird нет | Использовать DELETE / пересоздание |
