# Как пишем новые статьи (регламент конвейера)

Решение владельца (2026-09-23): каждая новая статья проходит **три мнения
→ сборная солянка → вычитка владельцем на сайте**. Конвейер описан здесь,
чтобы не изобретать заново.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Писатели | Gemini (`agy -p`), Kimi (`kimi -m kimi-code/k3 -p`) | Пишут статью по единому ТЗ, независимо друг от друга |
| Писатель/редактор | ассистент сессии | Пишет свою версию; затем собирает солянку: факты и точность — приоритет у kimi, слог и заголовок — у Gemini, структура/ссылки/frontmatter — у ассистента |
| Читатель | владелец | Перечитывает на сайте (локально или на проде) и доправляет сам |

## Шаги

1. **ТЗ** (готовит ассистент): аудитория и поисковый запрос, фактическая
   база (версии, порты, команды — сверенные по официальным докам
   firebirdsql.org), структура, объём 400–700 слов, Markdown H1+H2,
   1–2 таблицы, «что почитать дальше» темами. Одно и то же ТЗ всем троим.
2. **Генерация**: `docs/drafts/<id>.md` от каждого писателя
   (`agy_<id>.md`, `kimi_<id>.md`, версия ассистента сразу в
   `site/src/content/docs/<id>.md`).
3. **Солянка**: ассистент собирает финал в `site/src/content/docs/<id>.md`.
   Правило: факты не «побеждают голосованием» — спорное сверяется
   с официальной документацией; при сомнении выбрасывается.
4. **Сборка и проверки**: `npm run build` (валидация frontmatter-схемы),
   `tools/check_rendered.py` — чистота вывода.
5. **Вычитка владельцем**, затем публикация (коммит+пуш+redeploy —
   по явной команде).

## Frontmatter новой статьи (схема обязательна)

```yaml
---
title: "Человекочитаемый заголовок"
old_id: <slug>          # = имя файла = будущий URL /<slug>/
section: intro|install|errors|sql|glossary|groups
type: article|term|landing
date: YYYY-MM-DD        # дата публикации (для страницы «Что нового»)
updated: YYYY-MM-DD     # дата последнего содержательного изменения (опц.)
firebird:
  since:                # версия появления конструкции (для терминов)
  until:
  deprecated: false
---
```

## Новости (ежемесячные дайджесты): правила

Формат: один дайджест на месяц, `/novosti-YYYY-MM/`, секция `news`,
`date` — последний день месяца; хаб `/novosti/`.

1. **Пишет ассистент из собранной коллекции фактов** (источники:
   firebirdsql.org/en/news, ibase.ru, Google-группа firebird-general,
   топик «Новости» группы «СУБД Firebird»). Конвейер трёх мнений —
   для авторских статей; к компиляции дат и фактов LLM-писателей
   не привлекать (галлюцинируют списки).
2. **Фильтр значимости**: релизы самого Firebird, русская документация,
   ключевые инструменты экосистемы, безопасность, крупные события.
   Мелкие биндинги и точечные апдейты — мимо или одной строкой
   в «мелочью».
3. **РЕД База Данных — форк**: освещаем только главное (ключевые релизы,
   влияние на развитие Firebird), НЕ еженедельную ленту их канала.
4. **В новости — только польза читателю.** Внутренние планы сайта
   («проставим флаги версий», «сверим с нашей схемой») в дайджесты
   не пишем: им место в «Что нового» и ROADMAP. Правило введено после
   правки владельца 2026-09-24.
5. Даты постов из телеги уточнять перед публикацией карточки
   (в веб-ленте видны только времена).
6. **Каждый пункт новости — со ссылкой на первоисточник** (тред
   Google-группы, официальный анонс firebirdsql.org/ibase.ru, блог или
   репозиторий автора). Пункт без ссылки не публикуется. Ссылки добыть
   и проверить, не выдумывать: стабильный вариант — публичный тред
   группы `groups.google.com/g/firebird-general/c/<id>`; URL репозиториев
   брать из текста анонса или поиска, никогда не конструировать по
   памяти. Правило введено после правки владельца 2026-09-24 («ссылок
   нет — где искать tragach?»).



## Правила контента

- Русский язык; код/команды — как есть, байт в байт.
- Внутренние ссылки абсолютными путями: `[текст](/slug/)` — на
  существующие страницы; несуществующие цели сначала проверить по
  `legacy/pages.json` и списку статей.
- Заголовок H1 один; разделы H2; глубже — по необходимости.
- Честно о недостатках, без маркетинговой воды — тон справочника.
- Каждый факт, которого нет в ТЗ, помечается на вычитку: `[фактчек: …]`
  в черновике, чтобы владелец видел спорные места (в финале пометка
  снимается или факт удаляется).

## Вычет за уроки (не повторять)

- Имена переменных/параметров сверять с официальной докой, не по памяти
  (урок REMARK_SITE/SITE).
- Факт «репликации из коробки нет» оказался ложным — встроенная
  физическая репликация есть с 4.0. Не утверждать ничего о версионных
  фичах без сверки с release notes.
- **Писатели умеют писать файлы.** kimi (а возможно и agy) в проектной
  директории читает AGENTS.md и сам создаёт страницы в
  `site/src/content/` по нашей схеме — прямо во время генерации мнения.
  Поэтому: генераторов гонять из нейтральной директории (`cd /tmp`),
  вывод — только в `docs/drafts/`; после каждого прогона смотреть
  `git status` на предмет незваных файлов; в `site/src/content/` пишет
  только ассистент на шаге сборки.
- Даты в frontmatter — строкой в кавычках (`date: "2026-09-23"`):
  незакавыченная дата парсится YAML-ем как объект Date и валит схему.
